# NÁLEZY

## 🔴 BLOCKER

### B1. `start-dev.ps1` nespojí dev stack dohromady — port 8080 vs 8081

`start-dev.ps1` startuje backend bez `PORT`, tedy na **8080**. Ale `frontend/.env.local` má `REACT_APP_PROXY_TARGET=http://127.0.0.1:8081`. Navíc na tvém stroji **na 8080 už něco poslouchá** — odpovídá tam Windows http.sys s `HTTP Error 404`, ne Spring.

Výsledek: frontend naběhne, backend naběhne (nebo spadne na obsazeném portu), ale **nemluví spolu**. Čistý `.\start-dev.ps1` na tomto stroji tedy nedá funkční aplikaci.

**Ověřeno:** `GET http://localhost:8080/health` → http.sys 404; po ručním spuštění s `PORT=8081` → `Tomcat started on port 8081`, vše funguje.

**Oprava:** buď v `start-dev.ps1` nastavit `$env:PORT` podle `.env.local`, nebo `.env.local` vrátit na 8080 a uvolnit port. Ideálně skript ať port přečte z `.env` a při obsazení to řekne nahlas.

### B2. Přímé otevření `/search/catalog` se nikdy nedonačte

Když se `/search/catalog` otevře **přímým URL / refreshem** (ne proklikem v aplikaci), stránka nikdy nedosáhne `document.readyState === "complete"`. Prohlížeč hlásí „page still loading" i po 45 s, injektáž skriptů selhává, stránka je pro automatizaci i pro uživatele „živá mrtvola".

Proklik v aplikaci (SPA navigace na `/search/catalog` z `/sources`) funguje normálně — `readyState: complete`, 52 tlačítek, 28 inputů.

**Podstatná souvislost:** Vite dev proxy má `timeout: 0, proxyTimeout: 0` (`vite.config.ts` ř. 149-150). Když se spojení na backend jednou zasekne (typicky když Vite naběhne dřív než backend — což `start-dev.ps1` dělá vždy, viz B1), požadavky **nikdy neselžou ani nevyprší** — visí donekonečna a stránka se nikdy nedonačte. Ověřeno: `fetch('/api/auth/me')` přes proxy nikdy nedoběhl, tentýž dotaz přímo na `:8081` doběhl za **5 ms**. Po restartu Vite se to spravilo.

Tohle je s vysokou pravděpodobností **kořenová příčina** i nálezu, který samostatně našel druhý tester (viz S6 níže) — „aplikace po přihlášení na desítky sekund zmrzne, prázdný DOM".

**Oprava:** nastavit v proxy rozumný `timeout`/`proxyTimeout` (např. 30 s) místo 0, a v aplikaci mít u API klienta klientský timeout, aby uživatel dostal chybu místo nekonečného spinneru.

## 🟠 VYSOKÁ

### V1. AI komentář na homepage padá na NullPointerException (HTTP 500)

`POST /api/homepage/ai-commentary` → **500**, `java.lang.NullPointerException` v `Map.of(...)`.

Přesné místo, dohledáno ve zdrojáku — `service/homepage/HomepageAiCommentaryService.java`, metoda `generateVerbose()`, ř. ~62-72:

```java
if (data != null && data.get("error") != null) {
    return Map.of(
        "text", null,          // ← Map.of() nepovoluje null hodnoty
        "reason", "Widget vrací chybu dat: " + ...,
        "summary", null,       // ← totéž
        "fallback_used", false);
}
```

`Map.of()` vyhodí NPE na `null` hodnotě. Ironií je, že tahle větev je právě ta **ošetřovací** — má uživateli hezky říct „widget vrací chybu dat". Místo toho spadne celý request. Takže kdykoli widget na homepage vrátí data s klíčem `error`, dostane admin 500 místo srozumitelné hlášky.

**Oprava:** `new LinkedHashMap<>()` nebo `Collections.unmodifiableMap(...)`, případně `HashMap` s `put()`. `Map.of` s možnými `null` hodnotami je past — projít i ostatní výskyty.

### V2. Textový widget nejde po vytvoření upravit (dashboard i admin homepage)

Po vytvoření widgetu typu „Text" otevře tlačítko *Upravit* panel, který **neobsahuje pole pro nadpis, podnadpis ani obsah** — nabízí jen ŠÍŘKA / VÝŠKA / POZADÍ / BARVA GRAFU a „POPISEK" (což je UI pro grafové widgety). *Uložit* pak zapíše `config.caption = ""` místo `config.content`.

**Příčina, dohledáno ve zdrojáku** — `frontend/src/components/admin/AdminWidgetCanvas.jsx:712`:

```js
const isTextWidget = widget?.type === "markdown";
```

Widgety se ale všude (create formulář, DB, API) ukládají jako `type: "text"` (ověřeno `GET /api/me/dashboard/pages/{id}/widgets` → `"type":"text","engine_type":"text"`). Porovnání tedy nikdy nesedí a větev s poli Nadpis/Text (ř. 1961-2021) se nevykreslí nikdy.

Komponenta je sdílená mezi `/admin/homepage` a `/my-dashboard` → **týká se obou míst**.

Dobrá zpráva: backend `config` merguje po klíčích (`MeDashboardService.mergeConfig`), takže původní `content` nezmizí. Je to funkční mezera, ne ztráta dat.

**Oprava:** `widget?.type === "text" || widget?.type === "markdown"`.

### V3. FRED: vyhledávání s názvem země nebo s ID řady vrací nulu

Reprodukováno **naostro proti živému FRED API s platným klíčem** (`fred_api_key_configured: true`, konektor `up`):

| dotaz | výsledků | čas |
|---|---|---|
| `unemployment` | 5 | 1,4 s |
| `unemployment rate` | 5 | 3,4 s |
| `inflation` | 5 | 1,2 s |
| **`Germany`** | **0** | 2,9 s |
| **`GDP Germany`** | **0** | 11,4 s |
| **`unemployment Germany`** | **0** | 3,8 s |
| **`DEURHARMMDSMEI`** (platné FRED series ID) | **0** | 9,2 s |

Obecné anglické termíny fungují (ale vrací jen americké řady), jakmile je v dotazu **země**, výsledek je prázdný. A nenajde se ani přímo zadané ID existující řady — to je docela zásadní, uživatel co ví, co hledá, to nenajde.

Navíc: prázdné odpovědi trvají 9–11 s, tedy nejdéle ze všech.

**Kde hledat:** `CatalogIndexStore.searchSource()` pro `source='fred'` + schéma `classic_catalog_search.sqlite` — buď se název země neindexuje do prohledávaného pole (je jen v `full_path`/kategorii, ne v `title`), nebo víceslovný FTS dotaz vyžaduje výskyt všech tokenů v jednom poli.

### V4. Došeptávač řadí české dotazy podle amerických řad

`GET /api/catalog/suggest?q=inflace` → první nabídky jsou FRED „10-Year Expected Inflation", „11-Year Expected Inflation", ECB „HICP - Sugar - Spain". Pro `q=hdp` → FRED „Gross Domestic Product (GDP); Total, Transactions" (US Flow of Funds).

Přitom hlavní vyhledávání nad **stejným indexem** vrací pro `{source:"csu", query:"inflace"}` na prvních místech „Harmonizovaný index spotřebitelských cen (HICP) - měsíční/roční" se skóre 800+ a `_geo_adjustment: "row_default_czech_priority"`.

**Příčina:** `CatalogSuggestService.suggest()` (ř. ~36-100) řadí jen podle `_match` z `indexStore.ftsSuggest()` + `CatalogSourceRegistry.sourceBonus()`. Chybí mu geo/jazykový boost, který hlavní vyhledávání má. Došeptávač prostě běží jinou, jednodušší scoring cestou.

**Bonus (NÍZKÁ):** došeptávač nefunguje na prefix — `q=infl` → 0 návrhů, `q=inflace` → 6 návrhů. Typeahead, který vyžaduje dopsat celé slovo, moc typeahead není. Chybí FTS5 prefix syntaxe (`token*`).

### S1. Manager Explorer si nenajde data, která v katalogu prokazatelně jsou

Dotaz „Jak si vede bankovní sektor v Česku z hlediska ziskovosti a úvěrů?" (`banking_finance`, CZ):

- `query-understanding` **funguje výborně** — segment `banking_finance`, země `CZ`, confidence 0,9, zdroj `openai`
- `/api/explore/sector` vrátí 4 sektorové + 5 makro indikátorů; nejlepší sektorový match je ale položka s názvem **„bankovní sektor"** (dataset `1200:SPCTHOBJW0O2210CT0T000N`) se zdůvodněním „Shoda s dotazem … v katalogu ČNB - ARAD" — tedy shoda na jméně, ne na obsahu
- `leading_indicators`: **0**
- AI shrnutí (`/api/explore/summarize`, doběhlo v pořádku) pak logicky napíše: *„…nelze z čistě datového pohledu přesně vyhodnotit, protože chybí přímé časové řady k ziskovosti i úvěrům… nemáme doložený trend čistého zisku, ROE/ROA ani marží…"*

**Jenže ta data tam jsou.** Obyčejné `POST /api/catalog/search {source:"arad"}` nad stejným zdrojem najde:

| dotaz | první výsledky |
|---|---|
| `zisk bank` | `ROE_BANKS_PILOT` — **Rentabilita bank (ROE)**; `1013:SBBBM06931` — Bilance obchodních bank, Zisk/ztráta |
| `rentabilita ROE bank` | `ROE_BANKS_PILOT`; `1036:DBDZZQ30` — **rentabilita aktiv (ROA)** |
| `úvěry domácnostem` | `1175` — Úvěry MFI Domácnosti; `1164:SUCM102211XXX101101` — Úvěry klientské, Domácnosti |

Tedy: **discovery vrstva Explorer u je výrazně slabší než prosté katalogové vyhledávání nad týmž zdrojem.** AI pak poctivě řekne „nemám data" a uživatel odejde s tím, že aplikace nic neumí — přestože data má.

**Doporučení:** nechat Explorer pro každý manager intent zavolat `CatalogClassicSearchService` (nebo search-v2) s konkrétními termíny („ROE", „zisk", „úvěry", „NPL") místo jedné obecné shody na názvu segmentu.

### S2. Explorer tiše zahodí geografické omezení

Když se `/api/explore/sector` zavolá s `geo_mode: "countries", countries: ["CZ"]` (bez pole `country`), odpověď obsahuje:

```
country: "Svět (globální kontext)"
geo: { mode: "none", country_codes: [], display: "Svět (globální kontext)" }
```

…a to i když `question_understanding` ve **stejné odpovědi** správně říká `geo_mode: "countries"` a otázka výslovně zní „v Česku". S polem `country: "CZ"` už to funguje (`geo.country_codes: ["CZ"]`, 4 sektorové + 5 makro indikátorů).

Nejde ani tak o to, které pole je „správné" — jde o to, že se **rozpor mezi pochopeným záměrem (CZ) a použitým rozsahem (svět) nikde neohlásí**. Analýza tiše proběhne pro celý svět a tváří se jako odpověď na otázku o Česku. To je nejhorší druh chyby: špatný výsledek, který vypadá správně.

**Doporučení:** buď akceptovat obě varianty payloadu, nebo vrátit `400`. A když se `question_understanding.geo_mode` neshoduje s výsledným `geo.mode`, přidat do odpovědi varování.

## 🔵 NÍZKÁ / poznámky

- **`/api/auth/me` vrací pro nepřihlášeného `200` s prázdným tělem**, ne `401` (`AuthController.me()` → `return null`). Frontend to zvládá, ale jakýkoli klient, co se dívá jen na status kód, si bude myslet, že je přihlášený. Ověřeno.
- **FRED/BIS katalogy při výpadku vrací syrovou Java výjimku** — `502 {"detail":"ConnectException: null"}`. Pro srovnání ČSÚ vrací `503 {"detail":"Katalog ČSÚ se teď nepodařilo načíst. Zkuste to znovu později."}` a OECD `200` s `errors[]`. Chce to sjednotit.
- **Neznámý `source` vrací tiše 0 výsledků** místo hlášky „Neznámý zdroj pro katalogové vyhledávání." (`CatalogClassicSearchService`, ř. 25-27 — `normalizeSearchSource()` neznámé řetězce nevyprázdní).
- **Hláška „Výsledky z rychlého AI výběru zdrojů" se zobrazí i když AI plánovač selhal** a použil se deterministický fallback (`AI planner: nepouzit · duvod: LLM_CONNECT_TIMEOUT · deterministic fallback pouzit` v logu). Zavádějící.
- **„Katalog se načetl, ale neobsahuje žádné položky pro procházení"** je jedna generická hláška pro tři různé backendové odpovědi (prázdná 200 / 502 / 503). Backend přitom strukturovaně rozlišuje `errors[]`/`warning`/`stale`/`catalog_rescue` — dalo by se to promítnout do zprávy.
- **CORS:** s `REACT_APP_DEV_PROXY=false` (přímé volání backendu místo proxy) selže preflight na hlavičce `X-CSRF-Token`. Dokumentovaná varianta „vypnout proxy" tedy nefunguje out of the box.
- **Stack trace v chybových odpovědích** — chybové JSONy obsahují celý `trace`. Prověřeno: způsobuje to Spring Boot DevTools v dev režimu, `application-prod.yml` má `include-message: never`. **Není to produkční problém**, ale doporučuji do prod profilu explicitně přidat `server.error.include-stacktrace: never`, ať to nezáleží na tom, jestli se do runtime nedostane devtools.
- **`/my-dashboard` → `/` není bug.** `ProtectedRoute.jsx` / `SubscriberRoute` se chová správně (`!user` → `/`, ne-předplatitel → `/predplatne`, admin zůstane). Ověřeno ve 4 scénářích včetně nově založeného free účtu. Drobnost: přesměrování proběhne tiše, bez hlášky „pro zobrazení se přihlaste".
- **TradingEconomics** hlásí `misconfigured` — chybí `TRADING_ECONOMICS_API_KEY`. Konfigurace, ne chyba.
- **Zastaralý JAR** — viz úvod. `build/libs/bankintel-api-0.1.0-SNAPSHOT.jar` je z 4. 8., třídy z 21. 8.

# CO FUNGUJE DOBŘE

**Vyhledávání nad lokálním indexem** je silné. ČSÚ, ARAD a Eurostat vrací vysoce relevantní výsledky s viditelným zdrojem, jednotkou, `full_path` i skórovacími metadaty. České dotazy mají geo prioritizaci (`row_default_czech_priority`). Diakritika bez problémů. Prázdný dotaz → čistá hláška „Zadejte alespoň 2 znaky." SQL-injection-like vstup i nesmyslný vstup bezpečně zpracovány, `limit` robustně clampnutý na 1–100.

**Deep search (search-v2)** funguje naostro. „inflace Česko": AI plánovač správně určil `intent: find_series`, `geographies: ["CZ"]`, vygeneroval 10 exact + 10 sémantických termů. Výsledek: **8 verifikovaných řad**, top 5 = ECB HICP CZ, ČSÚ „Inflace - druhy", IMF WEO CZE.PCPIEPCH, ČSÚ Index spotřebitelských cen. Celý pipeline 13,5 s (planner 2,0 s, FTS 0,6 s, vector 0,1 s, reranker 4,8 s, ověření náhledů 2,1 s, odpověď 3,3 s). Opakovaný dotaz z cache: **62 ms**.

**Náhled dat / grafy.** `POST /api/catalog/preview` pro ČSÚ HICP vrátil 169 reálných řádků, 13 indikátorů, 167 ms. Grafová vrstva se vykresluje správně — na `/chart-system-demo` napočítáno **15 Recharts kontejnerů, 32 SVG surfaces, 43 vykreslených křivek/sloupců** (charty se mountují lazy, takže těsně po loadu jsou ještě prázdné — to je v pořádku).

**AI chat nad grafem funguje výborně.** Nakrmil jsem `/api/chart-agent/ask` reálnými ČSÚ daty a zeptal se česky na vývoj inflace a největší skok. Odpověď za **4,6 s**, česky, a hlavně **fakticky správně**: správně popsala pozvolný růst 99,3 → 115,1 mezi 2013–2021 a správně identifikovala rok 2022 jako zlom (115,1 → 132,1, +17,0 bodu) jako největší skok v řadě. Žádná halucinace, čísla sedí na vstupní data. Nabídla i pokračování.

**Ostatní AI plochy ověřeny:**
- `/api/chart-agent/intent` — „Přidej do grafu meziroční změnu" → `intent: compute_or_transform`, `catalog_query: "HICP year-over-year change"` + 4 varianty. Správně.
- `/api/catalog/explain-series` — `ai_used: true, source: openai`, věcně správný český výklad HICP.
- `/api/explore/query-understanding` — segment i geo správně, confidence 0,9.
- `/api/explore/summarize` — asynchronní job doběhl (`status: completed`) s českou odpovědí.
- `/api/magazines/ai/chat` — funguje, korektně degraduje („K dotazu jsem v archivu nic relevantního nenašla.") — seed PDF je jen 3,6 KB placeholder.

**Odolnost.** Když bylo OpenAI nedostupné (sandbox), `SearchV2Service` správně detekoval `LLM_CONNECT_TIMEOUT` (3 s connect timeout) a přepnul na deterministický fallback místo nekonečného čekání. Degradace zdrojů je většinou slušně ošetřená (ČSÚ 503 s českou hláškou, OECD 200 s `errors[]`, OECD2/3 410 Gone s odkazem na náhradu).

**Auth a bezpečnost.** JWT cookies (`httpOnly`, `SameSite=Lax`) + CSRF double-submit fungují správně. Bez `X-CSRF-Token` hlavičky → 403. Route guardy (`SubscriberRoute`) se chovají přesně podle kódu. Žádná cesta k obejití `/api` prefixu (`/explore/geo-options` bez `/api` → 404).

**Dashboard.** Vytvoření stránky funguje (`POST /api/me/dashboard/pages` → 200, 145 ms, správný slug, `access_mode: owner_only`). Seznam stránek, widgetů, homepage render — vše 200.

**Čtečka/archiv.** Magazíny (2 čísla, `ingest_status: ready`), detail čísla, seznam odkazů, PDF se servíruje (`application/pdf`, 200). Fulltext ve vydání vrací 0 hitů — ale seed PDF má 3,6 kB, takže to je očekávané.

- **PDF čtečka s reálným obsahem** — dev seed obsahuje jen 3,6 kB placeholder PDF. Listování, zoom, fulltext, inline grafy v článku a odkazy na grafy je potřeba otestovat na skutečném čísle časopisu.
- **MongoDB cache Manager Exploreru** (`manager_series_cache`) — Mongo v testovacím prostředí neběželo. Aplikace to ustála bez pádu (`MongoAutoConfiguration` je vyloučená v `application.yml`), ale chování s naplněnou cache neověřeno.
- **Vytvoření widgetu přes API** — `POST /api/me/dashboard/pages/{id}/widgets` mi vrátilo 400 (validace DTO), nedohledal jsem správný tvar payloadu. Přes UI to testoval druhý tester (viz V2).
- **Podcasty, RSS monitoring, odesílání e-mailů (Resend)**, exporty do PPTX/XLSX/PDF.
- **Živé grafy z externích zdrojů v UI** — ověřeno na úrovni API (data se stahují správně), ne proklikem celé cesty výsledek → graf → přidání druhé řady → uložení.
- **Stabilita nálezu B2 v běžném prohlížeči** mimo automatizaci — reprodukováno v Chrome i v headless Chromiu, ale stojí za nezávislé ověření ručně.
